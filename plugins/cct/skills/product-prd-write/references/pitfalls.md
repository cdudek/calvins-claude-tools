# Common pitfalls

Each one maps to a rule in `SKILL.md`. Symptom, consequence, fix.

## 1. Solution on page one (rule 1)

**Symptom:** the first heading after the title is "Solution" or a feature list.
**Consequence:** the team argues about the feature before anyone agreed on the problem.
**Fix:** move it below the line. Page one is problem, segment, metric, non-goals.

## 2. No evidence under the problem (rule 2)

**Symptom:** "We believe users have this problem."
**Consequence:** the team questions whether the problem is real, and is right to.
**Fix:** one quote, one number, one support theme, each with a source and a date. None available? No PRD yet: discovery.

## 3. Metric written after the feature (rule 3)

**Symptom:** the metric table is empty or says "engagement".
**Consequence:** nothing can fail, so nothing is learned.
**Fix:** one metric with a baseline and a target before the solution is written. One guardrail.

## 4. "Users" (rule 4)

**Symptom:** the segment column says users, customers, people.
**Consequence:** every reader pictures a different person and the solution serves none.
**Fix:** a segment with a size and a source.

## 5. No non-goals (rule 5)

**Symptom:** no section says what this is not.
**Consequence:** scope creep; stakeholders expect what was never planned.
**Fix:** non-goals on page one, and a Won't-have bucket in the requirements.

## 6. Written in one go (rules 7, 8, 11)

**Symptom:** a complete ten-section document appears the week before kickoff.
**Consequence:** nobody has read it; the decisions in it were made alone.
**Fix:** page one the day the idea lands; one section per product review.

## 7. Same detail for every size of work (rule 10)

**Symptom:** a two-day fix has a launch plan and a risk table.
**Consequence:** the document costs more than the fix, and the next one is skipped entirely.
**Fix:** a small change stays on page one. Detail follows risk.

## 8. Decisions in Slack (rules 12, 13)

**Symptom:** "didn't we decide this?" three weeks later.
**Consequence:** the question is reopened and answered differently.
**Fix:** the Decisions table: date, question, call, who, rejected and why. Appended, never rewritten.

## 9. Several owners, or none (rule 15)

**Symptom:** the Owner line names a team.
**Consequence:** nobody updates it and nobody can approve it.
**Fix:** one name. Everyone else in the RACI line.

## 10. Too prescriptive (rule 18, and the anti-pattern)

**Symptom:** pixel sizes, button colours, exact copy in the PRD.
**Consequence:** design has nothing to design; the PRD becomes a waterfall spec that is wrong by review two.
**Fix:** solution at the shape level. Requirements as EARS sentences. Design owns the rest.

## 11. Never edited down (rule 19)

**Symptom:** the document only grows.
**Consequence:** fewer readers every week until none.
**Fix:** delete something every time it is touched.

## 12. Launch readiness as a date (rule 21)

**Symptom:** "Launch: March 14."
**Consequence:** support learns on March 14, from customers.
**Fix:** the readiness checklist with a name on each line: support, legal, marketing, FAQ, rollout.

## 13. Stakeholders see the first draft (rule 22)

**Symptom:** review comments are the red team.
**Consequence:** credibility spent on things a ten-minute pass would have caught.
**Fix:** the red-team pass in `SKILL.md`, before anyone else reads it.

## 14. No Impact section (rule 23)

**Symptom:** the document ends at launch.
**Consequence:** nobody knows whether it worked, so the same bet is placed again.
**Fix:** the Impact table, filled on the date the metric table names. The PRD is done then, not at ship.
